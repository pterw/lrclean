# Releases 0.1.1 to 0.2.0: design

Brainstormed and approved section by section on 2026-11-26, then corrected after an outside read whose rows were each
verified against the code. It is the roadmap of the train to 0.2.0: what each release holds, what is done, and what a
later session settles before a plan is written. 0.1.1 was released on 2026-11-27. This file is tracked, so it carries no name, path
or measurement from a real library.

## Goal

Implement the fixes and features of the issue list in steps, so that the tool gives other users more choice while it
stays as strict by default as 0.1.0. The users are photographers, most of them not programmers: setting it up and
running it must be simple to follow, and every safety rule of 0.1.0 holds unless a line in the configuration lowers
one of the settings named under 0.2.0.

## Why lrclean, next to the tools that exist (research, 2026-11-26)

- **Lightroom Classic 15.4.1 and later** groups byte-identical files of the open catalog into stacks and offers to
  remove the extras from the catalog or delete them from the disk. It sees only photos imported into that one catalog.
  15.4 was withdrawn because deleting in that view could also delete originals; 15.4.1 fixed it.
- **Plug-ins** (Teekesselchen, Duplicate Finder) build a collection of suspected duplicates in one catalog.
- **General duplicate finders** (dupeGuru, Czkawka) compare files and know nothing of catalogs, so a removal can
  break a path a catalog records. **PhotoSweeper** (macOS only) works with a Lightroom Classic catalog and can mark
  duplicates rejected there instead of deleting them; it does not run on Windows, and does not check across many
  catalogs or against verified archive copies.
- **Synchronize Folder** compares one folder with one catalog. Lightroom has no lookup across catalogs.

No tool found compares the files on disk with many catalogs (one main catalog and many per-shoot catalogs), requires a
verified backup before anything leaves the drive, moves in two steps with an undo, and writes the evidence of every
row. That is lrclean's ground. Its weak side is the start: a hand-written JSON file, many commands and checks made by
hand. The releases below work on that side without loosening a default.

### The audit

0.1.1 waits for an audit of the current code, so that bugs a user would meet are found first.

1. **A situation matrix.** The situations a photographer can be in, each settled by a probe on a synthetic tree or by
   reading, each recorded as observed, inferred or untested: an archive or photo drive formatted exFAT or FAT32
   (coarse modification times, no file over 4 GB, file ids after a rename); a network archive; photos or catalogs on
   an external drive; the tool folder on another drive than the photos; online-only placeholders; one unreadable
   folder under a root; paths over 260 characters with long paths turned off in Windows, names over 240 characters,
   names holding `;` and non-Latin names; junctions, symbolic links, hard links and `subst` drives; two catalogs with
   the same name; Lightroom running, a stale lock, older or newer catalog formats; a full or stalling drive; a drive
   letter that changed; common configuration mistakes (single backslashes, a relative path, a missing key); the
   wrong Python version.
2. **Outside passes, run by Peter, read-only, at a fixed public commit** exported with `git archive` to a folder
   outside the tool folder: a read of the spec against the code (done, every row verified), a whole-repository read
   of the situations above, and an invariant checklist over the backup and move code run twice by a second model.
   Every returned row is verified by running it before anyone acts on it.

**What a finding does:** a confirmed bug whose fix is small and in the Standard lane (it decides no move, removal,
backup verdict or catalog read) joins 0.1.1. A Strict-lane or larger finding becomes an issue in the 0.1.2 or 0.2.0
milestone. Found so far and filed as issues: a `;` in a sidecar path splits it in the removal lists (a limit rule 35
already states, fails closed: the row is held; the guide does not say it yet); a destination name of 243 to 255 characters passes the manifest check and then fails to copy
(fails closed); whether an exFAT or FAT32 photo drive keeps a file's id across the rename into staging (unproven;
`stage` would hold every row); files behind a junction or link are left out without a word, and the scan still reads
complete; tool-folder writes with long paths turned off in Windows (unproven). The whole-repository read added, each
verified by a probe or by reading: a `live_catalog` or `old_states` entry that matches no scanned catalog is silent;
catalogs in a root removed from `catalog_roots` still decide; an archive or backup copy that became an online-only
placeholder after it was checked is still reported as copied (the later checks refuse it); `stage` and `purge` open
the work database inside a linked `work/` before they refuse it; two shoot folders with the same name can hide a
missing photo in `08_missing.csv`; an empty catalog root disconnected before `report` is not counted as a limit;
`verify` and the totals of the report's section 5 can mislead; one read error stops a whole `stage` or `purge`; a
stall during `stage` or `purge` ends with nothing printed; network-share paths; names ending in a space or a dot.

### Process

Tasks stacked, because most change `lrclean/cli.py`: each starts on its base plus the patches before it, and the
reviewed patches land as one stack with one gate run at the top. T1 is #16 and the exit codes; T2 the partial-root
messages, `verify <folder>` and the guide's lines; T3 the configuration refusals; #10 is split by file so it runs
beside T2: T4a records and reports the reason outside `cli.py`, T4b prints it. Each gets a short brief, one
implementer and one review that checks every statement against the code. As built (2026-11-26), every review asked
for fixes; a reviewed patch landed as reviewed and its fixes landed on top, grouped by file (FX-A to FX-D), each
re-reviewed. #13 is Light. One pull request, CI, the review bots
triaged; then `version` in `pyproject.toml` and `## 0.1.1 - <tag day>` in `CHANGELOG.md`. The tag waits for Peter's
word, the publish for his approval.

| #11 | A sidecar named `IMG_0001.ARW.xmp` belongs to `IMG_0001.ARW` in the reject check and the unrecorded-copies pass; one the catalog does not record is read from the files scan (rule 31 changes). |
| Leftovers of 0.1.1 | The link check tests a folder for a link before it lists it; the Lightroom check comes before a catalog's `-wal` is read; a process list that cannot be read gets its own message (exit 3 stays); `backup-run` finds the archive index once. |

Fourteen tasks. Most change `lrclean/cli.py`, so those run one after another, each on the patches before it, while
the backup, hash and report tasks run beside them. Each task's rule and guide text lands in the same commit as its
code. Reviewed patches land as stacks with one gate run at the top; fixes land on top, grouped by file, as in 0.1.1.

## 0.2.0

### Decided

- **One configuration file, `lrclean.toml`,** at the top of the tool folder, with comments. It holds the folders,
  the catalogs and a `[strictness]` section. When no `lrclean.toml` exists, `work/config.json` is read as in 0.1.0;
  when both exist, the tool refuses, names both files and tells the user to move or remove one; it never chooses for
  the user and never deletes either.
- **Three settings in `[strictness]`,** each defaulting to what 0.1.0 does:
  - archive copies required: two drives, one, or none (#14);
  - how old the scans may be: in 0.1.0 a check made by hand, which `preflight` takes over. The evidence rules of
    0.1.0 (a list must come from the latest catalogs scan, a catalog changed since its snapshot refuses) stay as they
    are and are not settings;
  - re-check depth: whether `stage` and `purge` re-read every archive copy in full (default) or accept a copy whose
    size and modification time are unchanged since `backup-verify` read it.
- **The pilot batch stays advice** in the guide, not a setting.
- **Never settings:** catalogs are never written; a photo with a pick, or with develop work, in any catalog that was
  read and is not in `excluded_catalogs` stays, with 0.1.0's one narrow exception for develop work (rule 26a: a
  byte-identical copy whose develop settings equal those of a twin that stays); a file that a live or shoot catalog
  records without rejecting it stays (a catalog that rejected it does not keep it, nor do the copies of the live
  catalog in `old_states`, except for their develop work and picks); removals come only from a list approved by its
  SHA-256; online-only placeholders are never opened; every move is journaled and can be undone until `purge`.
- **The three guards** of #14's comment: a lower setting comes only from a line in the file, never from a default, a
  command-line option or an environment variable; every summary and removal list records the settings it was made
  with; `purge` refuses a list approved under stricter settings than those in force, and a list made under looser
  settings shows them in its summary before it is approved.
- **`setup`** asks for the photo folder, searches the drives for catalogs (each drive with a time limit), lists them
  and asks which is the main catalog and which are its older copies (a role is never guessed from a name or folder),
  then writes a commented `lrclean.toml`.
- **`preflight`** runs the checks of "Before a real run" that the machine can make, one line each, and exits non-zero
  when one fails; the checks only a person can make are printed as reminders. It takes in #3 (each archive root's
  label and volume serial) and #2 (the set of paths the main catalog records that are missing).

### For the next session to settle

- The names and values of the three settings.
- How `purge`, which reads only the mover journal, learns the settings a list was made with (the `start` line of the
  `stage` journal is the one place it can); whether `stage` also compares them; whether a looser list is also
  confirmed once on the command line (#14 suggests it).
- Where the re-check depth gets an archive copy's size and modification time as `backup-verify` read it (the verified
  list holds neither today, and its header is checked exactly, so a list made before 0.2.0 needs a stated rule).
- What `archive copies = one` means when `archive_roots` names two or more roots.
- Whether `stage` and `purge` read the age of the scans too, or only `preflight` does.
- Where #3 records the drive identity, given that `backup-run` and `backup-verify` open no work database today (tests
  assert it); whether those commands, `stage` and `purge` refuse a changed serial or only `preflight` reports it; and
  which command writes the baseline of #2, so that a second `preflight` does not replace it.
- Whether `stage --apply` refuses when the missing-path set grew (#2).
- The list of `preflight` checks, and the questions `setup` asks and their order. For `setup`: single-quoted literal
  paths in the file it writes (a double-quoted `C:\Photos` is a TOML error); `lrclean.toml` in `.gitignore`; what it
  does when `work/config.json` exists; what it says when a drive's search hits its time limit; a comment that a
  synced cloud folder is not a backup, beside `archive copies = none`.
- The text for each backup level and re-check depth in `AGENTS.md`, the README's safety promises, the guide's
  "Backups come first", and rules 27, 32, 35, 41 and 50 and the two-root refusals of rule 33 of the existing design.

## Later

- **A simple window or local page** over the same commands, or a Lightroom extension.
- **Lightroom-side steps without an outside plug-in.** On the first library a third-party plug-in did the steps
  lrclean leaves to the user: flagging duplicates as rejects after the checks across catalogs, giving both copies the
  union of their keywords, collecting the staged photos, and removing the records of purged files by id with counts
  before and after. A small Lightroom plug-in of the project's own could read lrclean's lists and do these, without
  depending on the outside one.
